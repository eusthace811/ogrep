# Research for the release after 0.2.0

Research date: 2026-09-26. Primary papers, project documentation and source code were checked against zgrep at `15c0c5c`. These are experiment proposals, not achieved speedups. Keep the [release evidence](../PRODUCTION_REPORT.md) and [three required release tracks](IMPROVEMENT_PLAN.md) as the acceptance baseline.

## Conclusion

The measured 1.267x local speedup is not an algorithmic ceiling. It describes one workload on one workstation. The most promising next work is avoiding unnecessary verification and response work, controlling concurrent memory use, and providing a trustworthy refresh barrier. A different index or regex engine is a more expensive, conditional bet.

Our broad server workload barely improved in 0.2.0. At 1/4/16 clients, the load evaluation measured 30.8/68.5/79.8 requests/s and 527/868/1662 MiB peak server RSS. That does not establish the cause: server work, response size and the Python load generator all need separate measurements. The old server's reported `elapsed_ms` excludes final JSON assembly, serialization and transmission.

### First measurement from this research

The [new RPC profiler](../scripts/profile-rpc.py) ran the preserved 0.2.0 binary on the frozen Rust corpus: six ordinary file-list queries, one warmup each, nine randomized rounds, 60 independently checked responses. [Raw samples, hashes and provenance](../evidence/next-release/rpc-baseline.json) are retained. This is a sequential diagnostic, not a new release comparison.

For `fn main` (24,778 matching files), the median response was **4,858,576 bytes**, end-to-end time **152.85 ms**, client JSON decode **43.94 ms**, and the server's pre-serialization timer **30.04 ms**. An offline projection retaining only match type and path would be **1,891,766 bytes**, about **61% smaller**. This projection is not an implemented latency improvement. The receive interval also includes final server work and transport, so subtraction cannot isolate serialization cost. It does establish significant response work beyond verification and justifies testing compact replies first. Every measured response matched independent `rg -l -t rust` results.

**Implemented follow-up:** opt-in compact file replies now preserve old-client behavior and are used by the CLI. A subsequent 102-query server-backed CLI evaluation measured **1.111x versus 0.2.0 and 1.116x versus tgrep**, with 2,754 timed runs and independent ripgrep agreement for every query. The `fn main` direct-RPC example improved 2.12x, which must not be generalized to the whole workload. The [experiment report](../evidence/next-release/README.md) includes unfavorable medians, uncertainty, protocol tests and raw data. This is development evidence. The [combined 0.3.0 evaluation](../PRODUCTION_REPORT.md) now covers all three implementation tracks.

## Verification algorithms and execution

**1. Boolean matching and lazy location recovery.** Rust regex distinguishes existence, match positions and captures, and advises asking only for the needed information. Our hypothesis is to bypass location construction for eligible file-list/quiet requests. This is more than replacing `find` with `is_match`: zgrep normally matches individual LF-delimited lines, preserves CR, repairs invalid UTF-8 and supports inversion. A whole-file match can cross a newline when the line matcher cannot. Use a proven eligible subset or a line-based fallback; do not silently change Unicode or anchor behavior. [Regex performance guidance](https://docs.rs/regex/latest/regex/#performance).

**2. Private mutable matcher state per parallel job.** The regex documentation identifies contention when a shared regex searches short haystacks and recommends clones sharing compiled immutable data. Test this in the existing server before restructuring it. Rayon's `map_init` can own job-local state; it does not promise exactly one state object per OS thread. Clone frequency and warm-up cost belong in the measurement. [Rayon API](https://docs.rs/rayon/latest/rayon/iter/trait.ParallelIterator.html#method.map_init).

**3. Bounded parallel file verification.** Read/decode/match a bounded batch, then consume results in candidate order. Start with file-list output, where each result is small; avoid retaining every decoded file or every rendered line. Compare batch sizes and candidate-count thresholds at `-j 1/4/16`. Keep quiet cancellation, deterministic sorting, binary behavior and error handling explicit. Ripgrep's documented tradeoff between parallel output and sorted output illustrates why adding threads alone is insufficient. [Ripgrep FAQ](https://github.com/BurntSushi/ripgrep/blob/master/FAQ.md).

**4. Reusable literal finders, only where they add something.** `memchr::memmem::Finder` amortizes setup across haystacks. Try an eligible case-sensitive fixed-string path only if matching dominates; the current regex engine already extracts literals. Empty needles and UTF-8 boundaries need special treatment. ASCII-only matching cannot replace Unicode case folding. [memmem documentation](https://docs.rs/memchr/latest/memchr/memmem/index.html).

**5. Streaming verification and reusable buffers.** Many small files favor buffer reuse; very large files favor bounded streaming rather than whole-file decoding. `grep-searcher` separates searching from output sinks and already handles a substantial grep feature surface. A prototype could compare its scanner against ours, including multiline fallbacks. Adoption would require the entire output/encoding matrix, not just matching throughput. [grep-searcher](https://docs.rs/grep-searcher/latest/grep_searcher/).

**6. SIMD UTF-8 validation.** Test `simdutf8` only if decoding is a measurable cost on valid non-ASCII files. Preserve lossy repair maps and source offsets on invalid data, and portable CPU fallback. The existing ASCII path and filesystem overhead may leave little headroom. [simdutf8 implementation](https://github.com/rusticstuff/simdutf8).

## Server algorithms and resource control

**7. Compact, explicitly negotiated replies.** Add an opt-in path-only representation or parameter for file-list requests, used by our CLI and agents. Preserve legacy match rows for older callers. Avoid line copies, column vectors and nested `Value` objects when they are not consumed. Start by measuring response bytes and JSON decoding separately from the server's existing timer; do not label the whole difference “network overhead.” A compact offline projection can estimate removable bytes, but cannot establish an implemented speedup.

**8. Typed serialization and buffered direct writing.** `serde_json::to_writer` can eliminate a final whole-response `String`. Borrowed typed rows could also remove the intermediate `Value` tree. These are distinct savings. Buffer writes to avoid tiny socket writes; account for partial responses and disconnects. A streaming protocol needs explicit framing, cancellation and compatibility rather than silently changing one-response-per-line RPC. [serde_json writer API](https://docs.rs/serde_json/latest/serde_json/fn.to_writer.html).

Further local inspection found a smaller experiment to try first: `handle_search` embeds its existing match `Value` array in `json!`, then `json_rpc_result` embeds that result in another `json!`. The pinned serde_json 1.0.149 macro routes expression values through `to_value`, reconstructing these already-built trees. Moving the values into maps, or serializing a typed envelope directly, may remove substantial allocation without changing the protocol. Measure this separately from compaction; it has not been implemented or credited in the results above.

**9. Admission control and bounded queues.** Limit expensive in-flight search work, hold the permit through response disposal/transmission, and keep a separate route for status/refresh control. Bound queued work and connection resources too: a semaphore behind unlimited accepted threads merely moves the problem. Tower's concurrency-limit and load-shedding components illustrate the two separate policies; our synchronous server need not adopt Tower itself. Evaluate successful throughput and rejected/queued requests separately. [Concurrency limits](https://docs.rs/tower/latest/tower/limit/concurrency/index.html), [load shedding](https://docs.rs/tower/latest/tower/load_shed/index.html).

**10. SIEVE instead of eager LRU promotion.** SIEVE uses visited bits and eviction-time decisions rather than moving objects on each hit. It is a credible response to our cache's hit-promotion write phase, but the paper evaluates web caches. Our byte-sized decoded files, broad scans and mutation invalidation differ. First replay measured zgrep cache traces against LRU and SIEVE; then measure lock contention, hit ratio, memory and churn. Preserve byte caps and the generation check preventing old disk reads from repopulating invalidated content. S3-FIFO is another lazy-promotion/quick-demotion candidate if one-hit scan pollution is substantial. [NSDI 2024 paper and presentation](https://www.usenix.org/conference/nsdi24/presentation/zhang-yazhuo), [authors' cache design discussion](https://www.usenix.org/publications/loginonline/sieve-cache-eviction-can-be-simple-effective-and-scalable).

**11. Coalesce concurrent cache misses and cache compiled plans.** A bounded per-path in-flight read can prevent several requests decoding the same uncached file. A bounded compiled-query cache can avoid repeated pattern setup. These are local design hypotheses, conditional on miss/compile profiles. Keys must include encoding and matcher options; miss publication must carry the content generation. Cancellation, failed reads, memory bounds and adversarial unique queries need tests. Start with measured repeated-query and simultaneous cold-query workloads; do not hide cold compilation by reporting only hot loops.

## Refresh completion as a useful new function

**12. A publication barrier with a precise contract.** Watchman's synchronization cookies establish an ordering point in the notification stream, but its documentation describes platform limitations, including FSEvents ordering. A cookie observed by a watcher is insufficient for zgrep if indexing and publication are still queued. A portable initial implementation should reconcile eligible files and acknowledge only after publishing successful changes; polling/no-watch need their own path. State the treatment of edits concurrent with refresh. A failed or timed-out refresh must not report success. [Watchman synchronization](https://facebook.github.io/watchman/docs/cookies).

**13. Opaque instance/generation tokens.** Return a server-instance identity and completed publication generation so a caller can wait for known work without comparing wall-clock timestamps. Restart must invalidate old tokens rather than accidentally satisfy them. Watchman's clocks avoid relying solely on wall-clock file timestamps; its subscription flush waits for a defined delivery boundary. These are design references, not a claim that zgrep already implements the same guarantees. [Clockspec](https://facebook.github.io/watchman/docs/clockspec), [subscription flush](https://facebook.github.io/watchman/docs/cmd/flush-subscriptions).

Potential CLI/agent behavior: `refresh` returns only on success or explicit failure/timeout, followed by indexed searches. Retain `freshness=current` as a filesystem scan. A later targeted refresh accepting edited paths and expected content hashes could make an agent's own write-search loop cheaper; directory/ignore changes, deletion and concurrent writers prevent a naive path-only implementation from replacing full reconciliation.

## Larger algorithmic bets

**14. SIMD intersection and density-adaptive postings.** SIMD galloping is relevant to skewed posting sizes; block compression reduces memory traffic, and Roaring uses containers suited to different densities. We already have lazy posting reads, sparse probes and positional residue masks, so these are not automatic wins. Our postings carry masks as well as file IDs. Benchmark complete candidate production and final verification, not just integer decode speed. Include index size, startup pages, construction and update costs. [SIMD compression/intersection paper](https://arxiv.org/abs/1401.6399), [Roaring study](https://arxiv.org/abs/1709.07821).

**15. Selective full positions or packed content.** Zoekt uses positional trigrams and selects rare pairs at the required distance; its shards also contain file content. Our hypothesis is a selective positional sidecar for ambiguous literals, or a content pack reducing many-small-file opens. Neither replaces the existing compact mask without evidence: extra disk/RAM, rebuild work and freshness coupling are real costs. Our previous sparse-gram experiment was already rejected on measured tradeoffs. [Zoekt design](https://github.com/sourcegraph/zoekt/blob/main/doc/design.md), [selective-gram implementation](https://github.com/sourcegraph/zoekt/blob/main/index/indexdata.go).

**16. Batched asynchronous I/O.** `io_uring` can amortize submission/completion overhead. Consider it only after reads/syscalls dominate, and compare warm versus genuinely cold file data. Many small files also incur open/stat work; block-device IOPS are not grep latency. Keep a portable fallback and bound queue depth. [Original io_uring paper](https://kernel.dk/io_uring.pdf).

**17. Derivative-based extended regex.** RE# (POPL 2025) provides input-linear matching with intersection, complement and restricted lookarounds using symbolic derivatives. This is an interesting new query capability and an alternative to some backtracking cases. It is not a compatible replacement for arbitrary backreferences, our Unicode/offset rules or all regex workloads. Prototype separately using representative patterns and adversarial cases; compare compile time, memory and exact semantics as well as search throughput. [Microsoft Research publication and paper](https://www.microsoft.com/en-us/research/publication/re-high-performance-derivative-based-regex-matching-with-intersection-complement-and-restricted-lookarounds/).

**18. Batch queries sharing one candidate read.** An agent often asks several related questions about the same tree. A `search_batch` API could combine candidate sets, read each relevant file once and retain per-query identities/results. RegexSet is a possible boolean verification primitive; positional output still needs its own matcher. This is a product hypothesis rather than a current speed claim. Compare against concurrent separate searches with realistic overlap, cancellation and per-query limits; reject a batch plan that unnecessarily reads the union for every query. [RegexSet documentation](https://docs.rs/regex/latest/regex/struct.RegexSet.html).

## Evaluation rules

1. Preserve 0.2.0 and tgrep binaries, hashes, clean frozen corpus revisions and index provenance. Keep old release evidence unchanged.
2. Instrument normal query semantics. `--stats` requests full totals and can defeat ordinary file-list short-circuiting. Separate diagnostic timings from final uninstrumented timings.
3. Change one mechanism at a time; keep rejected experiments with their measurements. Measure real requests and full output correctness, not only kernel microbenchmarks.
4. Randomize/interleave repeated runs. Report per-query ratios and paired uncertainty alongside aggregate geometric means. A confidence interval over one host does not prove portability.
5. Cover broad/selective/absent queries, line output/file lists/counts, repeated/unique patterns, Unicode/invalid UTF-8, cold/warm data, tiny/large files and concurrent mutations.
6. For service tests report response bytes, client parse cost, server CPU/RSS, p50/p95/p99, accepted throughput, queueing/rejections and errors at 1/4/16 clients. Isolate the generator if it saturates; retain raw samples.
7. Require correctness gates before claiming an improvement. Do not trade false negatives, weaker freshness, omitted errors or unbounded memory for a speed ratio. Apply [Rebar's workload-oriented perspective](https://github.com/BurntSushi/rebar): engine rankings on selected regex tasks cannot establish application-wide superiority.

The adopted implementation order was profiling and compact replies, source-read reuse, bounded service work, then the refresh contract. These are now implemented and covered by the [combined release evaluation](../PRODUCTION_REPORT.md). Boolean verification, matcher scratch reuse, JSON-tree allocation removal and content-identity reuse remain useful next experiments; the original proposals and development measurements above are retained.
